## 1. GTDの工程と、画面・関数の対応

発注者が「構想（GTD・ロードマップ様式）」と「実装（画面・関数）」を一目で結べるようにするための表（1.3）。関数はすべて `src/domain/` に置く純粋な関数で、画面はこれを呼ぶだけにする。

| 工程 | 人間が判断すること | 仕組みに任せること | 画面 | ドメインの関数 |
| --- | --- | --- | --- | --- |
| 収集 | 何を入れるか（評価せずに入れる） | 収集日時を付けて収集箱の末尾に置く | 共通の収集の入力欄 | `capture` |
| 明確化 | 行動が要るか／複数ステップか／次の一手と、その扱い（今やる・任せる・日時が決まっている・後でやる） | 決めた結果を正しい置き場に作る。収集日時を引き継ぐ。全部作るか何も作らない | 収集箱（1件ずつ・一括） | `clarify`、`clarifyBulk` |
| 整理 | どの置き場が正しいか、終わったか、どのプロジェクトに属するか | 移しても id・作成日時・収集日時を保つ。完了日時・移動日時を記録する。参照の整合を守る | 次のアクション、連絡待ち、プロジェクト、いつか・多分、資料 | `editItem`、`completeItem`、`uncompleteItem`、`deleteItem`、`moveItem`、`completeProject`、`deleteProject` |
| 層とテーマ（年・四半期） | 年次目標の文章、重点テーマ、やらないこと、プロジェクトをどの四半期に置くか | テーマ7件の固定、年度×テーマ・年度×四半期で1件、重点テーマは3つまで。年次目標とプロジェクトのつながりをテーマと年度から導く | 年次目標・四半期、ロードマップ | `setAnnualGoal`、`toggleFocusTheme`、`setWontDo`、`placeProject`、`fiscalQuarterOf` |
| 週次レビュー（手作業） | 各置き場を見て直す | 件数と状態を表示する（判定はしない。4.3） | ホームと各画面を、週次レビューの順に並べた切替 | `projectSummaries`（件数を数えるだけ） |
| データの保存と受け渡し | いつ書き出し・読み込むか、どの端末を使うか | 自動保存、検証、書き出し・読み込みの日時と端末名の記録 | 共通の画面（書き出し・読み込み・状態の表示） | `parseExportText`、`serializeExport`、`validateState`、`transferStatus` |

## 2. 画面の一覧と遷移

### 2.1 画面の一覧

画面の切替は、週次レビューで見て回る順（10章の手順書の①〜⑥）に並べる。ホームは先頭に置く。

| 順 | 画面（切替の表示名） | URL | 主な内容 | 機能 |
| --- | --- | --- | --- | --- |
| 0 | ホーム | `#/` | 収集箱の未処理件数、今の四半期、進行中のプロジェクトと件数 | F08 |
| 1 | 収集箱 | `#/inbox`、`#/inbox/clarify`（`/2`・`/3`） | 未処理の一覧、1件ずつの明確化（質問ごとのURL）、一括振り分け | F01・F02 |
| 2 | 次のアクション | `#/next` | 未着手のアクションの一覧 | F03 |
| 3 | 連絡待ち | `#/waiting` | 待ちの連絡待ちの一覧 | F03 |
| 4 | プロジェクト | `#/projects`、`#/projects/<id>` | 一覧と、プロジェクトごとの詳細 | F04 |
| 5 | いつか・多分 | `#/someday` | 一覧 | F03 |
| 6 | 資料 | `#/reference` | 一覧 | F03 |
| 7 | 年次目標・四半期シート | `#/plan` | 年度 × テーマの年次目標、4つの四半期シート | F05・F06 |
| 8 | ロードマップ | `#/roadmap` | テーマ × 四半期の表 | F07 |

- URLの `#/...` は、決まった値だけを受け付ける（知らない値はホームにする）。`#/projects/<id>` の id が無ければ、プロジェクトの一覧にする（D14）
- 年度の切替（年次目標・四半期シート、ロードマップ）はURLに持たない。開くたびに今の年度から始める
- URLで決めるのは、どの画面を出すかだけ。URLから操作（読み込み・消去など）は起こさない。id はUUIDの形かを確かめてから探し、読めないURLは例外を捕まえてホームにする。画面のタイトル（`document.title`）にはプロジェクト名などの利用者の文字を入れない（ブラウザの履歴の同期で端末の外に出るため）
- 明確化の途中は、質問を進めるたびに履歴を1つ積む（`#/inbox/clarify` → `/2` → `/3`）。スマホの「戻る」は［前の質問に戻る］と同じ動きになり、質問1での「戻る」は［やめる］と同じになる。確定と［やめる］では、途中の質問の履歴を戻してから移る（確定の後に「戻る」で前の項目の質問に戻らないように）。まだ進んでいない質問のURL（再読み込みなど）は、進んだところまでに置き換える。確認画面が開いているときの「戻る」は確認画面を閉じる（D14）

### 2.2 遷移

```
共通の画面（全画面の上部）── 収集の入力欄 ── Enter で収集箱へ登録（画面は移らない）
        │
        ├─ ホーム ──「明確化を始める」──→ 収集箱（1件ずつの明確化）
        │      └─ プロジェクト名 ──→ プロジェクトの詳細
        ├─ 収集箱 ── 1件ずつの明確化 ── 確定 ──→ 次の項目（空になったら「収集箱は空です」）
        │      └─ 一括振り分け
        ├─ 次のアクション／連絡待ち ── プロジェクト名 ──→ プロジェクトの詳細
        ├─ プロジェクト ──→ プロジェクトの詳細 ── 次のアクション・連絡待ちを足す／完了／移す／削除
        ├─ いつか・多分／資料 ── 移す ──→ （移動先の入力）
        ├─ 年次目標・四半期シート ── 主要プロジェクト ──→ プロジェクトの詳細
        └─ ロードマップ ── カード ──→ プロジェクトの詳細
```

### 2.3 PCとスマホの画面の切替

- **PC**（幅720px以上）：共通の画面の下に、切替のタブを横一列に並べる（9つ）。上部に固定するのは収集の入力欄の行だけで、切替のタブはスクロールで流れる位置に置く（2つを固定すると本文が狭くなるため）。9つが入りきらない幅では、タブの並びの中だけを横にスクロールする
- **スマホ**（幅720px未満）：既存PoCと同じく、下部に固定のタブバーを置く。使う頻度の高い4つ（ホーム、収集箱、次のアクション、プロジェクト）と「メニュー」。「メニュー」を押すと、連絡待ち・いつか・多分・資料・年次目標・四半期シート・ロードマップを、週次レビューの順に並べたメニューを出す。収集箱のタブには未処理の件数を数字で添える

| 要素 | 内容 |
| --- | --- |
| 収集の入力欄 | 画面の上部に固定し、スクロールしても隠れない。ラベルは「収集箱に入れる」、入力欄の中の薄い文字は「思いついたことを入力して Enter」。Enter（日本語入力の変換中の Enter を除く。`isComposing`、`keyCode 229`）か「入れる」ボタンで登録する。前後の空白を除いて空なら登録せず、ボタンも押せない。500字まで（入力欄の下に、超えたときだけ「500字までです（今 512字）」と出す） |
| 登録した表示 | 入力欄の下に「収集箱に入れました（未処理 4件）」を3秒ほど出す（読み上げにも伝わる `role="status"`）。入力欄は空になり、フォーカスは入力欄に残る（続けて入れられる） |
| 書き出す | 状態全体をJSONで書き出す（6章）。端末名がまだ無ければ、先に端末名を入れる小さな画面を出す。読み取り専用のタブ（6.3）では押せない（古い内容を別の端末に渡さないため） |
| ⋯（データのメニュー） | JSONを読み込む／退避したデータを書き出す（あるときだけ）／このブラウザの名前を変える／表示の切替（端末に合わせる・ライト・ダーク）／使っている容量の表示／このブラウザの保存データを消去 |
| 受け渡しの状態 | このブラウザの端末名（まだ付けていなければ「このブラウザ（名前なし）」）、最後に書き出した日時、最後に読み込んだ日時とその書き出し元（端末名と書き出し日時）。書き出した後に変更があれば「（書き出し後の変更あり）」と添える（D13）。まだ無いものは「まだありません」。**「書き出しましょう」などの指示は出さない**（12.2） |
| 保存の状態 | 保存に失敗したとき、読み取り専用になったとき、起動時に保存データを読めなかったときだけ、共通の画面の下に消えない帯を出す（6.3）。正常なときは何も出さない。PRプレビューでは、常に「プレビュー：実際のデータを入れないでください」の帯を出す（8.3） |
| 元に戻す | 画面の下部（スマホではタブバーのすぐ上）に「〇〇しました［元に戻す］［×］」を出す（6.4） |

- スマホでは、画面の上部に固定するのは、収集の入力欄・［入れる］・［書き出す（アイコン）］・［⋯］の1行だけにする。受け渡しの状態（短く「書き出し 11/3 20:15（書き出し後の変更あり）・読み込み 11/2」）は、その下のスクロールで流れる位置に置く（キーボードを開いたときに本文が見える広さを残すため）。入力欄は上部にあるので、画面のキーボードで隠れない。入力欄の文字は16px（スマホのブラウザが拡大しないように。既存PoCと同じ）

### 3.2 ホーム

状態の表示だけを置く。**結論・指示（「〜しましょう」「滞留しています」「次のアクションがありません」など）は出さない**（4.3・企画書8章）。

| 要素 | 内容 |
| --- | --- |
| 収集箱 | 「収集箱：未処理 N件」。ボタン［明確化を始める］（収集箱の1件ずつの明確化へ）。0件なら「収集箱：未処理 0件」とだけ出し、ボタンは出さない |
| 今の四半期 | 「2026年度 第3四半期（2026年10〜12月）」、重点テーマ（無ければ「未設定」）、主要プロジェクトの件数（「主要プロジェクト 4件（うち完了 1件）」）。四半期シートへのリンク |
| 進行中のプロジェクト | 表（名称、テーマ、置いた四半期、次のアクションの件数、連絡待ちの件数）。並びはテーマの表示順 → 名称順で固定。件数は「次のアクション 2件」「連絡待ち 0件」のように数字で出すだけで、0件を強調しない（4.3）。名称を押すとプロジェクトの詳細へ。進行中のものが無ければ「進行中のプロジェクト：0件」とだけ出す |
| そのほかの件数 | 次のアクション（未着手）N件、連絡待ち（待ち）N件、いつか・多分 N件、資料 N件。押すとそれぞれの画面へ |

### 3.3 一覧の共通のつくり（次のアクション・連絡待ち・いつか・多分・資料）

- 1行に1件。行の末尾の［編集］を押すと、その行がその場で編集の形に開く（入力欄と［保存］［キャンセル］［移す…］［削除］）。行の全体を押せる形にはしない（行の中のチェックボックス・プロジェクト名のリンクと、押す場所で動きが変わらないように）
- スマホでは、1行を「1行目：チェックボックスと内容、2行目：プロジェクト名・相手・日付などの小さな文字と［編集］」の2段にし、横スクロールなしに収める
- 完了の状態を持つもの（次のアクション・連絡待ち）は、行の先頭のチェックボックスで完了にする。完了にした行は一覧から消え、「完了にしました［元に戻す］」を出す
- 一覧の下に「完了したものも表示（N件）」のチェックボックス。入れると、完了したものを薄い文字と「✓完了 11/3」の表記で一覧の末尾に並べ、チェックを外すと完了を取り消せる（D8）
- 並びは作成した順（古い順）。並べ替え・絞り込み・検索は作らない（4.2）
- 空のときは「まだありません。収集箱から明確化すると、ここに置かれます」と出す（このときだけ次の手順を書く。ホームではないため）
- 削除は確認を出さず、「削除しました［元に戻す］」を出す（7.1）

| 画面 | 1行に出すもの | 編集できるもの |
| --- | --- | --- |
| 次のアクション | 内容、属するプロジェクトの名称（単独なら、テーマがあればテーマ名）、収集日 | 内容、属するプロジェクト（進行中のプロジェクトをテーマごとにまとめた選択肢と「単独」）、テーマ（単独のときだけ。任意）、メモ |
| 連絡待ち | 内容、相手、依頼日、属するプロジェクトの名称 | 内容、相手、依頼日、属するプロジェクト、メモ |
| いつか・多分 | 内容、収集日 | 内容、メモ |
| 資料 | 件名、本文の冒頭1行 | 件名、本文（行を開くと全文を出す） |

- 資料の本文などに書かれたURLは、ただの文字として出す（リンクにしない。8.3）

### 3.4 収集箱（一覧と一括振り分け）

```
収集箱  未処理 5件                                   [1件ずつ明確化する]
┌─────────────────────────────────────────────┐
│ □ すべて選ぶ                                         │
│ □ 〇〇〇〇〇〇〇〇                     10/30 21:04    │
│ □ 〇〇〇〇                             11/1  7:40    │
│ …                                                    │
└─────────────────────────────────────────────┘
選んだ 2件を  [次のアクションへ] [いつか・多分へ] [資料へ] [削除]
```

- 並びは古い順（先頭がいちばん古い）。各行に内容と収集日時
- **1件ずつ明確化する**：先頭の項目から始める（3.5）。特定の項目を選んで始める操作は作らない（「後回しにはしない」。6.1）
- **一括振り分け**（D9）：チェックした項目を、追加の入力が要らない4つの出口のどれかにまとめて送る。ボタンには件数と行き先を書く（「選んだ2件を次のアクションへ」）。確定後に「2件を次のアクションに置きました［元に戻す］」を出す。収集した文言が、作られるものの内容（資料なら件名）になる。プロジェクト・連絡待ち・2分・カレンダーは、1件ずつの明確化で行う
- 空のときは「収集箱は空です」
- スマホでも同じ形（各行はチェックボックス・内容・収集日時の2段）。一括振り分けのボタンは、項目を選んだときだけ、タブバーの上に固定して出す

### 3.5 明確化（1件ずつ）

収集箱の画面の中で、一覧の代わりに出す。上部に「収集箱 残り N件」と、取り出した項目の内容・収集日時を常に出す。出口を確定するまで、データは何も変わらない（入力の途中の内容は画面の中だけで持つ）。

- **入力は、確定か［やめる］まで保つ**：［前の質問に戻る］で戻っても、入れたプロジェクトの名称・目的とする成果・テーマ、書き直した次の一手、相手などは消さない
- 質問が切り替わったとき・確定の後は、フォーカスを次の質問の見出しへ移す（キーボードと読み上げで迷わないように）
- スマホでも同じ並び（質問 → 補足 → 選択肢を縦に）で、選択肢のボタンは横幅いっぱいにする

**どの質問にも、左下に［← 前の質問に戻る］（最初の質問では出さない）、右下に［やめる］を置く。** ［やめる］を押すと一覧に戻り、項目は収集箱の先頭に残る（「途中でやめても、この項目は収集箱に残ります」とボタンの近くに書く）。

#### 質問1：行動が必要か

| 要素 | 文言 |
| --- | --- |
| 質問 | **これについて、何か行動が必要ですか？** |
| 補足 | 行動とは、自分か誰かが実際に手を動かすこと（電話する、買う、書く、調べる など）。**決められないものは「いつか・多分」へ。** |
| 選択肢 | ［はい、行動が必要］→ 質問2へ |
| | ［いいえ、行動は要らない］→ 次の3つを出す |
| | 　［削除する］：「もう要らないもの」→ 確定。「削除しました［元に戻す］」 |
| | 　［いつか・多分に置く］：「今はやらないが、捨てたくないもの」→ 確定 |
| | 　［資料として残す］：「行動は要らないが、後で見返したい情報」→ 確定 |

#### 質問2：複数のステップが必要か

| 要素 | 文言 |
| --- | --- |
| 質問 | **終わらせるまでに、2つ以上の行動が要りますか？** |
| 補足 | 1回の行動では終わらないもの（例：旅行の準備、部屋の片付け）は「プロジェクト」にします。プロジェクトにしても、今決めるのは最初の一手だけです。 |
| 選択肢 | ［はい、プロジェクトにする］→ プロジェクトの入力（下）→ 質問3（プロジェクトの最初の一手） |
| | ［いいえ、1回の行動で終わる］→ 質問3 |

プロジェクトの入力（同じ画面の中に出す）：

| 入力欄 | 必須 | 初期値・説明 |
| --- | --- | --- |
| プロジェクトの名称 | ○ | 初期値は収集した文言。100字まで（収集した文言が長いときは、短くするよう入力欄の下に出す） |
| 目的とする成果 | ○ | 説明「終わったとき、どうなっていれば完了ですか？」。2,000字まで |
| テーマ | ○ | 7つのボタンから1つ選ぶ（初期値なし） |
| 置く四半期 | 任意 | 「置かない」（初期値）／今の年度と次の年度の8つの四半期から選ぶ（それ以外はプロジェクトの画面で直す）。説明「この四半期に終わらせる主要なプロジェクトだけ置きます」 |

［次へ（最初の一手を決める）］で質問3へ。

#### 質問3：次の一手と、その扱い

| 要素 | 文言 |
| --- | --- |
| 質問 | **次の一手は何ですか？** |
| 入力欄 | 初期値は収集した文言（書き直せる）。ただし、プロジェクトの最初の一手のときは空欄にする（名称と同じ文の次のアクションができないように）。500字まで、必須。説明「目に見える具体的な行動で書きます（例：『〇〇さんに電話して日程を聞く』）」 |
| 補足の質問 | **この一手をどうしますか？** |

選択肢（1つの画面で選ぶ。選ぶと、その下に出口ごとの入力欄と確定ボタンを出す）：

| 選択肢 | 補足 | 追加の入力 | 確定ボタン |
| --- | --- | --- | --- |
| 今やる（2分以内で終わる） | 2分以内で終わるなら、管理するより今やる方が早い（2分ルール）。やってから押してください | なし | ［やった（完了として記録）］ |
| 誰かに任せる | 自分より適任の人に頼み、返事を待つもの | 相手（必須、100字まで）、依頼日（必須、初期値は今日） | ［連絡待ちに置く］ |
| 日時が決まっている | 会議や約束など、その日時にやるものはカレンダーで管理します | なし（「お使いのカレンダーに登録してください。登録したら『登録した』を押すと、収集箱から消えます。このツールには残りません」と出す） | ［カレンダーに登録した］ |
| 自分で後でやる | 次のアクションの一覧に置き、時間のあるときに選んでやります | なし | ［次のアクションに置く］ |

- 「誰かに任せる」「自分で後でやる」には、任意で「属するプロジェクト」を選べる（進行中のプロジェクトを、テーマごとにまとめた選択肢。初期値は「なし（単独）」）。「自分で後でやる」で単独のときは、任意でテーマも選べる（12.2）
- 確定後に「〇〇に置きました［元に戻す］」（カレンダーなら「カレンダーへ送りました［元に戻す］」）を出す（D1）
- ［元に戻す］を押すと、その項目が収集箱の先頭に戻り、明確化の画面にその項目をもう一度、質問1から出す

**プロジェクトの最初の一手**（質問2で「はい」のとき）は、選択肢を「自分で後でやる」「誰かに任せる」の2つにし、上に次の補足を出す（6.1）。

> 2分で終わる一手はその場でやり、その次の一手を書いてください。日時が決まっている一手はカレンダーに登録し、その次の一手を書いてください。

確定ボタンは［プロジェクトを作る］。プロジェクトと最初の一手を同時に作る。

#### 確定の後

- 次の項目（収集箱の先頭）へ自動で進み、質問1から始める。「〇〇に置きました」を短く出す
- 収集箱が空になったら「収集箱は空になりました」と出し、［ホームへ］［一覧へ］を置く

### 3.7 年次目標・四半期シート（`#/plan`）

上部に年度の切替：［◀］「2026年度（2026年4月〜2027年3月）」［▶］［今の年度へ］。範囲は2000〜2099年度。

- 幅1280pxで、テーマの列120px・四半期の列4つで横スクロールなしに収める。1つのセルにカードが5枚程度なら縦に積む（G5）
- ドラッグで受け取るのは、このアプリのカードが入れた種類（`application/x-tmpoc-project`）の値だけとし、その値が存在するプロジェクトの id かを確かめてから移す（7.2・8.3）。ほかのアプリから落とされた文字は無視する。移す先の年度・四半期は、落としたセルから取る（受け取った値からは取らない）。テーマを変えないことは `placeProject` の側でも確かめる

- スマホ（幅720px未満）では、表を「テーマごとのブロックに、4つの四半期を縦に並べる」形に組み替える。移すのはカードのメニューで行う（7.1）

## 4. データの型

### 4.1 共通の約束

- 名前は英語、画面の表示は日本語（ラベルの対応表は `src/labels.ts` に1つだけ置く）
- **id**：`crypto.randomUUID()` で作る文字列（UUID v4）。すべての種類を通じて一意で、置き場の間を移しても変わらない。テストのために、ドメインの関数は id を作る関数を引数で受け取る
- **日時**：UTCの ISO 8601（`toISOString()` の形、例 `2026-11-03T09:41:58.000Z`）。**依頼日**だけは `YYYY-MM-DD`
- **今の時刻**：ドメインの関数は `now: Date` を引数で受け取り、中で `new Date()` を呼ばない（5.2）
- **端末の時計のずれへの備え**（D15）：日時を記録する関数は、前の日時より前にならないようにする。明確化で作るものの作成日時は「今」と「収集日時」の遅い方、更新日時は「今」と「前の更新日時」の遅い方、完了日時・移動日時は「今」と「作成日時」の遅い方。PCで作ったものを、時計が少し遅れたスマホで直したときに、日時の順序の検証（4.6）で読めなくなるのを防ぐため。「すべてのドメイン関数の結果が `validateState` を通る」ことを単体テストで確かめる
- **上限はドメインの関数でも守る**：作る・変える・移す関数は、文字数・件数・状態全体の上限（4.7）を超える結果を作らない（超えるなら、理由を返して何も変えない）。保存はできたのに次の起動時に読めない、という状態を作らないため
- **文字列**：前後の空白を除き、NFCに正規化してから保存する。必須の文字列は、空白を除いて空なら受け付けない。改行は、メモ・目的とする成果・年次目標・やらないこと・資料の本文でだけ受け付ける。改行とタブのほかの制御文字は受け付けない。文字数はコードポイント（見た目の1文字にほぼ等しい）で数える

### 4.2 型（`src/domain/types.ts`）

```ts
/** テーマ（7件固定。状態やJSONには持たず、コードの定数とする。5.1） */
type ThemeId = "work" | "startup" | "health" | "relationships" | "finance" | "hobby_learning" | "other";
const THEMES: readonly { id: ThemeId; label: string }[]; // 仕事／起業／健康／人間関係／家計／趣味・学び／その他 の順

type Quarter = 1 | 2 | 3 | 4;
interface Placement { fiscalYear: number; quarter: Quarter } // 2000〜2099年度

/** すべての要素（テーマを除く）に共通 */
interface Base {
  id: string;
  createdAt: string;      // 作成日時
  updatedAt: string;      // 更新日時（作成時は作成日時と同じ）
}

/** 置き場の要素に共通（明確化で作られたもの・移したもの） */
interface Placed extends Base {
  capturedAt: string | null; // 収集日時。明確化で作られたら元の項目から引き継ぐ。画面から直接足したものは null
  movedAt: string | null;    // 最後に置き場の間を移した日時。移したことが無ければ null
}

interface InboxItem extends Base {
  text: string;           // 内容（500字）
  capturedAt: string;     // 収集日時（＝作成日時）
}

interface Action extends Placed {
  text: string;                 // 内容（500字）
  projectId: string | null;     // null なら単独のアクション
  themeId: ThemeId | null;      // 単独のアクションだけが任意で持つ。プロジェクトに属するなら必ず null
  status: "todo" | "done";      // 未着手／完了
  completedAt: string | null;   // 完了のときだけ持つ
  note: string;                 // メモ（2,000字。空でよい）
}

interface WaitingFor extends Placed {
  text: string;                 // 内容（500字）
  party: string;                // 相手（100字、必須）
  requestedOn: string;          // 依頼日 YYYY-MM-DD（必須）
  projectId: string | null;
  status: "waiting" | "done";   // 待ち／完了
  completedAt: string | null;
  note: string;
}

interface Project extends Placed {
  name: string;                 // 名称（100字、必須）
  outcome: string;              // 目的とする成果（2,000字、必須）
  themeId: ThemeId;             // 必須
  placement: Placement | null;  // 置く四半期（0か1つ）
  status: "active" | "done";    // 進行中／完了
  completedAt: string | null;
  note: string;
}

interface SomedayItem extends Placed { text: string; note: string }
interface ReferenceItem extends Placed { title: string; body: string } // 件名 500字、本文 10,000字

interface AnnualGoal extends Base {
  fiscalYear: number;
  themeId: ThemeId;
  text: string;                 // 到達状態（2,000字、必須。空にしたら年次目標そのものを消す。PR 2a で決定）
}

interface QuarterSheet extends Base {
  fiscalYear: number;
  quarter: Quarter;
  focusThemeIds: ThemeId[];     // 重点テーマ（0〜3、重複なし。選んだ順）
  wontDo: string;               // やらないこと（2,000字。空でよい）
}

/** 状態全体（localStorageに保存し、JSONに書き出すもの） */
interface AppState {
  schemaVersion: 1;
  inbox: InboxItem[];           // 先頭がいちばん古い
  actions: Action[];
  waitingFors: WaitingFor[];
  projects: Project[];
  someday: SomedayItem[];
  references: ReferenceItem[];
  annualGoals: AnnualGoal[];
  quarterSheets: QuarterSheet[];
}
```

**なぜこの形か**

- **置き場ごとに配列を分けた**：1つの配列に「種類」の項目を持たせる形より、種類ごとの必須の属性（連絡待ちの相手など）を型で守れる。発注者がJSONを開いたときも、置き場ごとにまとまって読める
- **主要プロジェクトは `Project.placement` だけで表す**：四半期シートには持たない（二重管理を避ける。12.1）
- **年次目標とプロジェクトのつながりは持たない**：プロジェクトのテーマと、置いた四半期の年度から導く（12.1）。導く関数は `annualGoalFor(state, project)`
- **カレンダーへ送ったもの・削除したものは何も残さない**（企画書4章①）
- **2分でやったものは、完了したアクションとして残す**（12.2）
- **端末名・書き出しと読み込みの日時は `AppState` に入れない**：ブラウザごとの設定であり、読み込みで別の端末の値に置き換わってはいけないため（8.5。6章）
- **スキーマv1に、すべての配列を最初から持つ**：節目2の時点で年次目標・四半期シートの画面が無くても、空の配列として持つ。実データを入れ始めた後にスキーマを変えて移行するのを避けるため（10章）
- **フェーズ2のための日時**（作成・更新・完了・収集・移動）をすべて記録する（4.3）。ただし、それを使って判定する関数は作らない

### 4.3 置き場の間の移動の表（5.3）

移動は `moveItem(state, source, target, input, now)` の1つの関数で行う。行が移動元、列が移動先。「—」は同じ置き場。収集箱は移動先にならない（5.3）。

| 移動元 ＼ 移動先 | 次のアクション | 連絡待ち | プロジェクト | いつか・多分 | 資料 |
| --- | --- | --- | --- | --- | --- |
| **次のアクション**（未着手） | — | 可。相手・依頼日（初期値は今日）を入力。属するプロジェクトは引き継ぐ。テーマは捨てる | 可。目的とする成果・テーマ（単独でテーマがあれば初期値）を入力、名称＝内容。属していたプロジェクトとのつながりは捨てる | 可。属するプロジェクト・テーマは捨てる | 可。件名＝内容、本文＝メモ。属するプロジェクト・テーマは捨てる |
| **連絡待ち**（待ち） | 可。属するプロジェクトは引き継ぐ。相手・依頼日はメモに書き足す | — | 可。名称＝内容。目的とする成果・テーマを入力。相手・依頼日はメモに書き足す。属していたプロジェクトとのつながりは捨てる | 可。相手・依頼日はメモに書き足し、属するプロジェクトは捨てる | 可。件名＝内容。本文＝メモ（相手・依頼日を書き足す） |
| **プロジェクト**（進行中） | 可（下の※）。内容＝名称。目的とする成果はメモに書き足す。テーマは単独のアクションのテーマとして引き継ぐ | 可（※）。内容＝名称。相手・依頼日を入力。目的とする成果はメモに書き足す。テーマは捨てる | — | 可（※）。内容＝名称。目的とする成果はメモに書き足す | 可（※）。件名＝名称。本文＝目的とする成果とメモ |
| **いつか・多分** | 可（単独のアクション。テーマは任意で入力できる） | 可。相手・依頼日を入力 | 可。名称＝内容。目的とする成果・テーマを入力 | — | 可。件名＝内容、本文＝メモ |
| **資料** | 可。内容＝件名、メモ＝本文 | 可。相手・依頼日を入力。内容＝件名、メモ＝本文 | 可。名称＝件名、目的とする成果・テーマを入力、メモ＝本文 | 可。内容＝件名、メモ＝本文 | — |

- **共通**：id・作成日時・収集日時は引き継ぐ。最後に移した日時（`movedAt`）と更新日時を記録する。メモは引き継ぐ。プロジェクトへ移すときは、置く四半期も任意で入力できる。名称・内容・件名は、移す画面で書き直せる（初期値は移動元の文言）
- **完了したもの（完了のアクション・連絡待ち・プロジェクト）は移せない**。完了を取り消してから移す（5.3）
- **書き足し**（D5）：移動先に無い文章は、メモの末尾に「相手：〇〇（依頼日 2026-11-03）」「目的とする成果：〇〇」の形で書き足す。書き足し・写しの結果が移動先の上限を超えるとき（メモが2,000字を超える、資料の本文をメモに写すと2,000字を超える、名称が100字を超える など）は、移さずに「〇〇が長すぎるため移せません。短くしてから移してください」と出す
- **※ プロジェクトを移すとき**（D4）：未完了の次のアクション・連絡待ちがあるなら移せない。完了した子だけなら、子は単独のものとして切り離す（`projectId` を null にする。内容は残る）。置く四半期は捨てる
- 移動の画面は、移動先を選ぶ → 必須の入力 → 「次のものは引き継がれません：属するプロジェクト」の表示 → ［移す］の順。確定後に「〇〇に移しました［元に戻す］」を出す（移すと捨てる属性があり、また移しても元に戻らないため。D1）
- 属するプロジェクトを変える（アクション・連絡待ちを別のプロジェクトへ、または単独に）のは移動ではなく、編集（`editItem`）で行う。`editItem` は、付け替え先が進行中のプロジェクトであることを確かめ、プロジェクトに属させたアクションのテーマを空にする（5.3。画面の選択肢だけに頼らない）

### 4.4 プロジェクトの子（次のアクション・連絡待ち）の扱い

| 操作 | 子の扱い | 確認・元に戻す |
| --- | --- | --- |
| 完了にする | 未完了の子を一緒に完了にする（D2）。子の完了日時は、プロジェクトの完了日時と、その子の作成日時の遅い方にする（時計の遅れた端末で、後から足した子を完了にしたときに、子の「作成日時 ≦ 完了日時」が破れないように。D15。PR 2a の点検で追記） | 確認なし。「プロジェクトと、未完了の N件を完了にしました［元に戻す］」 |
| 完了を取り消す | 子の状態は変えない（5.3） | なし（取り消しを取り消すには、もう一度完了にする） |
| 削除する | 確認画面で「一緒に削除する」か「単独のものとして残す」を選ぶ（初期値は残す。D3） | 確認画面（「次のアクション 2件・連絡待ち 1件（完了したもの 4件を含む）」と件数を出す） |
| 移す | 未完了の子があれば移せない。完了した子だけなら切り離す（D4） | なし |
| 子を足す | 進行中のプロジェクトにだけ足せる。完了したプロジェクトには足せない | — |
| 子の完了を取り消す | 属するプロジェクトが完了なら取り消せない（「先にプロジェクトの完了を取り消してください」）。完了したプロジェクトに未完了の子を残さないため | — |

### 4.5 ルールを守る関数の一覧（`src/domain/`）

### 4.6 JSON・localStorageの読み込みでの検証

`validateState` は `unknown` を受け取り、次のどれかに反したら、理由の一覧を返して何も取り込まない。理由は「次のアクションの3件目：内容が空です」のように、どこが悪いかが分かる日本語にする（多いときは最初の20件）。

- 外枠（書き出したJSONのとき。6.2）：`app` が `"taskmanagement_tool_poc"` と完全に一致し、`exportedAt` が実在するUTCの日時、`deviceName` が端末名の許可リストに合い、項目がこの4つだけ。外枠の無い生の状態は受け付けない（既存PoCのファイルなどを誤って読まないため）
- 形式：オブジェクトの項目が決まったものだけ（知らない項目は拒否）。`__proto__`・`constructor`・`prototype` のキーと入れ子の深さは、外枠を含む全体について、ほかの検証より先に確かめる
- 型：`unknown` を型ガードで絞る（`any` や `as` で検証をすり抜けない）。年度・四半期は `Number.isInteger` で確かめる。id の重複は `Map` で調べる
- スキーマの版：`schemaVersion` が 1。これより新しい版は「このアプリより新しい版のデータです。アプリを更新してから読み込んでください」で拒否
- id：UUIDの形で、すべての種類を通じて一意
- 文字列：型、上限の文字数（4.7）、必須のものが空白だけでない、改行を許さない項目に改行が無い、改行とタブのほかの制御文字が無い
- 列挙値：テーマID（7件）、状態、四半期（1〜4）、年度（2000〜2099）
- 日時：ISO 8601のUTCの形で、実在する日時。順序は 収集日時 ≦ 作成日時 ≦ 更新日時、作成日時 ≦ 完了日時 ≦ 更新日時、作成日時 ≦ 移動日時 ≦ 更新日時。収集箱の項目は収集日時＝作成日時。依頼日は実在する `YYYY-MM-DD`
- 状態と完了日時：完了のものだけが完了日時を持つ
- 参照：`projectId` が存在するプロジェクトを指す。`themeId` を持つアクションは単独のもの
- 完了したプロジェクトに、未着手のアクション・待ちの連絡待ちが無い
- 一意：年次目標は年度 × テーマで1件、四半期シートは年度 × 四半期で1件
- 重点テーマ：3つまで、重複なし
- 件数：各配列が上限以内。状態全体が600万字以内

読み込んだ値は、検証した項目だけを新しいオブジェクトに詰め替えて状態にする（スプレッドで丸ごと写さない。既存PoCと同じ）。

- 状態全体の大きさは `stateSize(state)`（`JSON.stringify` の文字数。UTF-16の単位）の1か所だけで数える。ドメインの関数も同じ関数で上限を確かめる（数え方が違うと、保存できたのに次の起動で読めない状態ができるため）
- 文字列が前後の空白を除いてNFCになっているかは検証しない（正規化は、ドメインの関数が書き込むときに行う。読み込みで弾くと、手で直したJSONなどが読めなくなるだけで、守るものが無いため）

### 4.7 文字数・件数の上限と容量の見込み（D10。8.2）

| 対象 | 上限 |
| --- | --- |
| 名称（プロジェクト）、相手、端末名 | 100字（端末名は16字） |
| 内容（収集箱・アクション・連絡待ち・いつか・多分）、資料の件名 | 500字 |
| メモ、目的とする成果、年次目標、やらないこと | 2,000字 |
| 資料の本文 | 10,000字 |
| 件数 | 置き場ごと（収集箱・アクション・連絡待ち・プロジェクト・いつか・多分・資料）に10,000件。年次目標・四半期シートは年度の範囲で決まる（最大 100年 × 7件、100年 × 4件） |
| 状態全体 | JSONにしたときに600万字まで（下の見込み） |
| 読み込むJSONファイル | 32MiB（下の見込み） |

**容量の見込み**

- localStorageは、同じオリジン（`yoheitaniguchi.github.io`）のすべてのアプリで合わせて約500万字（ブラウザによる）。保存はJSONの文字列で行う
- 1件の大きさは、項目名・id・日時だけで約300字、これに内容（平均40字程度）を足して約350字
- 1日10件を収集し、すべてが何かの置き場に残るとして、1年で約3,650件 × 350字 ≒ 約130万字。1日30件なら約380万字で、上限に近づく。削除・カレンダーへ送ったものは残らないので、実際はこれより少ない
- フェーズ1（12月の運用まで）では十分に収まる。1年使い続けたときに備える仕組み（完了したものを書き出して消すなど）は作らず、使っている容量を共通の「⋯」メニューに「このアプリの保存データ：約120万字」と数字で出すだけにする（警告はしない。8.2）。容量が問題になったら、変更要求として扱う
- 保存に失敗したら（容量超過など）、消えない帯で「保存できませんでした。今の内容はこの画面にだけあります。JSONを書き出して保存してください」と出す（8.2）
- **状態全体の上限は600万字**：件数 × 文字数の上限をかけ合わせると、理屈の上では1億字を超える。そこで状態全体の大きさにも上限を置き、ドメインの関数（4.1）と検証（4.6）の両方で守る。600万字は、localStorageに保存できる大きさ（約500万字）より少し大きい（保存に失敗しても、書き出しはできるように）
- **読み込みの上限は32MiB**：600万字がすべて日本語（UTF-8で1文字3バイト）でも、書き出したJSONは約1,800万バイトで、32MiBに収まる。保存できる大きさの3倍以上（8.2）。ファイルを読む前に、ファイルの大きさで確かめる（スマホのメモリを守るため）
- **書き出したJSONは必ず読み込める**ことを、上限いっぱい（600万字、日本語）の状態を書き出して読み込む単体テストで確かめる
- 起動時に読めなかった値の退避は1件だけにする（同じ容量を使うため）。読み込み・消去で回復したら、退避した値を消せる。使っている容量の表示に、退避した値も含める

## 6. データの保存と、PCとスマホの間の受け渡し（8.2・8.5）

### 6.1 保存するもの

| localStorageのキー | 中身 | JSONに書き出すか |
| --- | --- | --- |
| `taskmanagement_tool_poc:v1:state` | 状態全体（`AppState`） | 書き出す |
| `taskmanagement_tool_poc:v1:device` | このブラウザの設定：端末名、最後に書き出した日時、最後に読み込んだ日時と書き出し元（端末名・書き出し日時）、書き出し・読み込みのときの状態の指紋、このブラウザで最後に変更した日時、初めての説明を閉じたか | 書き出さない |
| `taskmanagement_tool_poc:theme` | 表示の切替（端末に合わせる／ライト／ダーク） | 書き出さない |
| `taskmanagement_tool_poc:corrupt-backup` | 起動時に読めなかった値の退避（1件だけ。別の値がすでに退避されていたら上書きしない） | 書き出さない（「退避したデータを書き出す」で `tmpoc-backup-<YYYYMMDD>-<HHMM>.json` として別に出せる） |

- PRプレビューでは、名前空間を `taskmanagement_tool_poc-pr-preview-<番号>:` にする（本番の保存データを読み書きしない。8.3）
- **Storage API（`localStorage`）に触るのは `src/domain/persistence.ts` だけ**にする。状態・ブラウザの設定・表示の切替・退避のどれも、ここの関数を通す（既存PoCでは `theme.ts` と `usePersistedState.ts` も直接触っていたので、移すときに直す）。ほかの場所からの参照は ESLint で禁じる（8.2）
- `v1:device` と表示の切替のキーは、同じオリジンのほかのアプリやPRプレビューからも書けるので、読むときに検証する。項目は決まったものだけ、端末名は許可リスト、日時は形式を確かめる。だめなら既定値（名前なし・記録なし）に戻す
- 「このブラウザの保存データを消去」は、この名前空間のキーをすべて消す

### 6.2 書き出しと読み込み

**書き出すJSONの形**

```json
{
  "app": "taskmanagement_tool_poc",
  "exportedAt": "2026-11-03T11:15:00.000Z",
  "deviceName": "PC",
  "state": { "schemaVersion": 1, "inbox": [], "...": "..." }
}
```

- ファイル名は `tmpoc-<端末名>-<YYYYMMDD>-<HHMM>.json`（端末の時刻。例 `tmpoc-PC-20261103-2015.json`）。`.gitignore` の `tmpoc-*` で除外される
- 書き出したら、このブラウザの「最後に書き出した日時」と、そのときの状態の指紋を記録する
- 読み取り専用のタブ（6.3）では、書き出しも、ブラウザの設定の書き込みもしない
- スマホのブラウザでも、ファイルのダウンロードで書き出せる。発注者のスマホは Android（Chrome）で、書き出したファイルは端末の「ダウンロード」フォルダに保存される。Googleドライブの受け渡し用のフォルダへは、Files アプリなどの共有（「ドライブ」へ送る）で移す。この手順は節目2の Android 実機の確認で確かめ、手順書（節目3）に書く

**読み込みの手順と確認画面**

1. ⋯ →［JSONを読み込む］→ ファイルを選ぶ（スマホではファイルの選択の画面で、Googleドライブなどから選べる）
2. ファイルの大きさ（32MiB）→ JSONとして読めるか → 禁止のキーと入れ子の深さ → 外枠 → 版 → 4.6の検証、の順に確かめる。だめなら理由を出して終わる（今のデータは変わらない）
3. 確認画面を出す

```
JSONを読み込みます（今のデータは置き換えられ、元に戻せません）

             読み込むファイル                このブラウザ（PC）
書き出し     スマホ が 11/3 20:15 に書き出し   最後に書き出した：11/2 22:00
最終更新     ―                                 最後に変更した：11/3 9:10
件数         収集箱 2・次のアクション 31 …     収集箱 0・次のアクション 28 …

⚠ 最後に書き出した後に、このブラウザで変更があります
   [今のデータを書き出す]

                                    [やめる]  [置き換える]
```

4. ［置き換える］で状態を置き換え、「最後に読み込んだ日時」と書き出し元、そのときの状態の指紋を記録する。「書き出した後の変更」は無しになる

- 確認画面の初期のフォーカスは［やめる］。［今のデータを書き出す］を押した後も確認画面は閉じず、「⚠」の行を「書き出しました（20:16）」に変える
- **「書き出した後の変更があるか」は、状態の指紋で決める**（`transferStatus`）：書き出し・読み込みのときに、状態をJSONにした文字列から短い指紋（ハッシュ。秘密を守るためのものではなく、同じかを比べるだけ）を作って覚えておき、今の状態の指紋と違えば「変更あり」とする。日時の比較にしないのは、状態とブラウザの設定を別々のキーに保存するため、保存の失敗などで両者が食い違っても誤らないようにするため。読み込みで置き換えたことは「変更」に数えない
- 「このブラウザで最後に変更した日時」は、表示のためだけに記録する
- 読み込むファイルの端末名も、表示の前に許可リストの検証に通す。だめならファイル全体を拒否する

**受け渡しの手順（手順書 `docs/weekly-review.md` に書く予定のもの）**

1. 使い終わった端末で［書き出す］。共有していない専用のクラウドのフォルダに保存する
2. 次に使う端末で ⋯ →［JSONを読み込む］→ そのファイルを選ぶ → 確認画面で、書き出し元と日時を見て［置き換える］
3. 読み込んだファイルと、それより古いファイルを、クラウドのフォルダから消す
4. 両方の端末で並行して変更しない（読み込んだ側の変更は失われる）

### 6.3 起動時の読込と、保存の失敗・複数のタブ

既存PoCのやり方（`usePersistedState`・`autosave`）を移して使う。

- 起動時の読込も 4.6 と同じ検証に通す。読めなければ、自動保存を止め、元の値を退避し、空の状態で上書きしない。帯で「保存データを読めませんでした。自動保存を止めています」と、［JSONを読み込む］［読めなかったデータを書き出す］［保存データを消去］を出す
  - ［読めなかったデータを書き出す］は、退避ではなく元のキーの値をそのまま書き出す（`tmpoc-backup-<YYYYMMDD>-<HHMM>.json`）。退避は容量の不足や前の退避があると書けないが、回復するまで元のキーは書き換えないため。退避できなかったときは、帯にその旨を書く
  - 回復するまでの画面の状態は空なので、［書き出す］と確認画面の［今のデータを書き出す］は使えなくし、「書き出し後の変更あり」も出さない（空のファイルを本物のバックアップと誤らないため）
  - 回復するまでは、読み込み・消去の確認画面に「読めなかった保存データは…消えます」と［読めなかったデータを書き出す］を置く（読み込みは元のキーを上書きし、消去は退避も消すため）
- 保存に失敗したら、消えない帯で知らせる（4.7）
- 読み取り専用のタブと、起動時に読めなかった保存データが残っている間（回復するまで）は、収集の入力欄を使えなくし、入力欄の下に理由を出す（入れても保存されないため）
- 別のタブで、この名前空間のデータのキー（状態・ブラウザの設定・退避。表示の切替は除く）が変わったら、または localStorage 全体が消されたら（`storage` イベント。`isDataKey`）、このタブを読み取り専用にし、帯で「別のタブで変更されました。このタブは読み取り専用です」と［再読み込み］を出す。収集の入力欄・書き出しも使えなくする（入れた内容が保存されない、古い内容を渡してしまうため）
- **保存データの消去**の確認画面にも、読み込みと同じく、書き出した後の変更があればその事実と［今のデータを書き出す］を置く。初期のフォーカスは［やめる］

### 6.4 「元に戻す」（D1）

- reducer が、元に戻せる操作の直前の状態と直後の状態を1組だけ覚えておく（保存はしない）。`undo` の操作は値を受け取らず、今の状態が直後の状態と同じオブジェクトのときだけ、直前の状態に戻す（ほかの変更が挟まっていたら戻さない）。任意の状態を外から置く操作は作らない（検証を迂回する経路を作らないため）
- 出す操作：明確化のすべての出口（1件ずつ・一括）、完了にする（アクション・連絡待ち・プロジェクト）、削除（アクション・連絡待ち・いつか・多分・資料）、置き場の間の移動
- 出さない操作：編集（その場で直せる）、完了の取り消し、プロジェクトの削除（確認を出すため）
- JSONの読み込み・保存データの消去・別のタブの変更を検知したときは、覚えていた組を捨てる（消去した後に戻すと、消したデータが復活して保存し直されるため）
- 表示は、次の操作をするか［×］で閉じるまで残す（時間で消さない。読むのが遅くても押せるように）。再読み込みすると消える
- 「元に戻す」で収集箱に項目が戻るのは、明確化の直後だけ（5.3の例外。D1）。新しい項目を作るのではなく、同じ id・収集日時の項目が元の位置に戻る
- 保存の直前の検証（既存PoCと同じ）は、最後の守りとして残す

## 8. テスト方針

- Vitest で、`src/domain/` の関数・JSONの入出力・localStorageの保存を単体テストする。テストのタイムゾーンは `Asia/Tokyo` に固定する（CIはUTCで動くため）
- テストのデータは架空のもの（「テスト用の項目1」など）だけを使う（8.3）
- 主なテスト

| 対象 | 確かめること |
| --- | --- |
| 年度と四半期 | 3/31と4/1、6/30と7/1、9/30と10/1、12/31と1/1の境界。UTCの前日15:00（日本時間の0:00）の境界 |
| 収集 | 末尾に追加、収集日時＝作成日時、空白だけは拒否、上限 |
| 明確化 | 8つの出口それぞれで、作られる要素・消える項目・引き継ぐ収集日時（6.4の表）。必須の入力が欠けたら何も変わらない。プロジェクトの最初の一手は2択だけ。完了したプロジェクトは選べない。一括振り分けの4つの出口 |
| 移動 | 移動の表（4.3）の各マス。完了したものは移せない。id・作成日時・収集日時が変わらない。書き足しと上限。未完了の子があるプロジェクトは移せない |
| プロジェクトの子 | 完了で子も完了、取り消しで子は変わらない、削除の2つの方法、完了したプロジェクトに子を足せない |
