## 1. 結論

- **企画書との整合**：ゴールの状態 G1〜G6 を満たす作りになっており、企画書の対象外（判定・警告、カレンダー連携、検索など）に踏み込んだところは見つからなかった。ずれではないが、企画書の言葉と実装の解釈に差がある点が1つ（G3 の「次のアクションが一覧で見える」を件数で満たしている。IMP-01）、データが増えたときに企画書8章「ホームでぱっと見える」が弱くなる点が1つ（IMP-02）ある
- **操作性**：明確化・収集・元に戻すの流れは、迷わず使える形になっている。Android の幅で、下部のタブの文字が2行に折れる・上部の固定部分に空きがある、といった表示の不具合がある（IMP-03〜IMP-05）。プロジェクトの詳細は、いちばん目立つボタンが「完了にする」で、ふだんの操作（次のアクションを足す）との強弱が逆になっている（IMP-06）
- **デザイン**：落ち着いた配色で、毎日見ても刺激が強すぎない点は良い。一方で、下線付きのリンクが多く、情報の多い画面（ロードマップ・一覧）で線が重なって騒がしい（IMP-09）。フォーカスを移したときに、質問の見出しに入力欄のような枠が出る（IMP-10）
- **セキュリティ**：コード・CI・依存関係に、新しい重大なリスクは見つからなかった（本番の依存の脆弱性0件、`@security` を含むテスト311件成功、CSP・ESLint の禁止・JSONの検証はそのまま効いている）。潜在的なリスクとして、**書き出したJSONの写しが端末の「ダウンロード」に残り続けること**（IMP-13）、**ブラウザの保存が「消されうる保存」のままであること**（IMP-07）、**読み込みの確認で書き出しを押し忘れると変更を失うこと**（IMP-08）の3つを挙げる
- **機能不足**：フェーズ1の範囲の中で足りないものは、上の IMP-01 のほかは無い。範囲外では、検索、次のアクションのまとまりごとの表示、繰り返しの用事、完了したものの整理などが、使い続けると必要になる見込みがある。いずれも企画書が対象外にしているため、変更要求の候補として記録した（CR-001〜CR-006）
- **データを失う不具合**（運用中でもすぐ直すもの）は、見つからなかった

### 3.1 IMP-01 プロジェクトの一覧とホームに「次の一手」の内容を1行添える（P2）

- **課題**：企画書3章の3は「各プロジェクトの次のアクションが一覧で見える」としている。今の一覧とホームは「次のアクション N件」の件数だけで、次に何をするかは、プロジェクトを1つずつ開かないと分からない
- **根拠**：`src/screens/ProjectsScreen.tsx`・`src/screens/HomeScreen.tsx` の表は件数の列だけ。`src/domain/summaries.ts` の `projectSummaries` は件数だけを返す。週次レビューの④（`docs/weekly-review.md` 1章）は「件数の列を目で見て、次の一手を足す」で、中身は見えない
- **対策**：
  1. `src/domain/summaries.ts`：`ProjectSummary` に `firstNextAction: string | null`（そのプロジェクトの未着手のアクションのうち、配列の先頭＝いちばん古いものの内容）を足す。並びの決め方は「`state.actions` の並び順の最初」だけにし、件数や日付で何かを判定しない
  2. `ProjectsScreen.tsx`：表の「目的とする成果」の列の右に「次の一手」の列を足す（1行に省略。`.project-table__outcome` と同じ省略の CSS）。無ければ「—」とだけ出す（「ありません」「未設定」などの文言、色、太字は使わない。CLAUDE.md 4.3）。スマホのカードにも同じ1行を足す
  3. `HomeScreen.tsx`：進行中のプロジェクトの表にも同じ列を足す（IMP-02 で列を減らした後の形に合わせる）
- **テスト**：`src/domain/summaries.test.ts` に、①未着手が複数あるとき先頭の内容、②完了したものだけなら null、③単独のアクションは数えない、④別のプロジェクトのものを拾わない、の4件
- **完了の確認**：架空のデータ（`roadmap-demo.json`）で、一覧とホームに次の一手が出る。0件のプロジェクトは「—」だけで、行の見た目が他と同じ
- **文書**：`docs/design.md` 3.2・3.6 の表に列を足し、変更履歴に書く
- **効果**：週次レビューの④で、プロジェクトを開かずに「次の一手が今も正しいか」を見て回れる。企画書3章の3を、件数ではなく中身で満たす
- **矛盾の確認**：表示を足すだけで、0件の強調・並べ替え・絞り込みはしないので、フェーズ2（③）の「検出」には当たらない

### 3.2 IMP-02 ホームの並びと、プロジェクトの表を短くする（P2）

- **課題**：企画書8章は、ホームで「収集箱の未処理件数とプロジェクトの状態を中心に、現在の状態がぱっと見えること」を求める。進行中のプロジェクトが20件になると、PC（1280px）でも1画面に収まらず、Android（幅412px）ではホームが縦に約5画面分になる。「置き場」（次のアクション・連絡待ちなどの件数）が最下部に追いやられる
- **根拠**：架空のデータ（プロジェクト20件）で確かめた画面。「置いた四半期」の列は「2026年度 第3四半期（2026年10〜12月）」の長い表記で、PCでも2行に折れて行が高くなる。Android のカードは1件5行
- **対策**：
  1. `HomeScreen.tsx` の並びを「収集箱 → 置き場の件数 → 今の四半期 → 進行中のプロジェクト」に変える（件数の小さなまとまりを先に、長い表を最後に）
  2. 「置き場」の件数は、箇条書きから横に並ぶ小さな枠（PC は4つを1行、スマホは2×2）にする。既存のトークン（`--surface`・`--border`）だけを使う
  3. プロジェクトの表の「置いた四半期」は、今の年度なら `quarterLabel(fy, q, { short: true })` から月を除いた「第3四半期」、ほかの年度なら「2025年度 第4四半期」と短くする（`src/domain/fiscal.ts` に `quarterShortLabel(placement, now)` を足し、テストを付ける）
  4. スマホのカードは「1行目：名称、2行目：テーマ・四半期・次のアクション N件・連絡待ち M件（IMP-01 を採ったら次の一手）」の2行にする
- **テスト**：`quarterShortLabel` の単体テスト（今の年度・前の年度・次の年度、年度の境界 3/31・4/1）
- **完了の確認**：架空のデータで、PC（1280×900）の最初の画面に、収集箱・置き場の件数・今の四半期が収まる。Android の幅（412px）で、プロジェクト1件が2行
- **文書**：`docs/design.md` 3.2 の表の順と内容を直す
- **効果**：プロジェクトが増えても、ホームを開いた最初の画面で全体の件数が分かる（企画書8章）
- **矛盾の確認**：並びと表記を変えるだけで、出す情報（件数と状態）は変えない。結論・指示の文言は足さない

## 4. 操作性

### 4.0 良い点（変えないもの）

- 明確化：確定するまで何も変わらず、どこでも［前の質問に戻る］［やめる］がある。確定のあとに「元に戻す」が出る。質問の補足が短く、マニュアルなしで判断できる
- 収集：どの画面からでも Enter で入り、続けて入れられる。入れた件数が出る
- 確認の画面は3つの操作（読み込み・消去・プロジェクトの削除）だけで、日常の操作は「元に戻す」で救う
- 画面の切替が週次レビューの順に並んでいる

### 4.1 IMP-03 Android の下部タブの文字が2行に折れる（P2）

- **課題**：下部のタブバーで「次のアクション」が「次のアクショ／ン」と2行に折れる（幅412px）。幅360pxでは「プロジェクト」も折れる。折れたタブは文字が読みにくく、ほかのタブと高さがそろわない。また、「メニュー」の文字だけが、ほかのタブより下にずれている
- **根拠**：`src/index.css` の `@media (max-width: 720px)` の `.tabs__tab` が `white-space: normal`。幅412px・360px で画面を開いて確かめた
- **対策**：

## 5. デザイン

### 5.0 良い点（変えないもの）

- 白とグレーを基本に、紫のアクセントを要所だけに使う落ち着いた配色で、毎日見ても疲れにくい。ダークモードも同じ考え方で整っている
- 今の四半期・重点・完了を、色だけでなく文字（「今の四半期」「重点」「✓完了」）でも示している
- 「必須」「任意」の印、入力欄のすぐ下の誤りの表示など、項目の意味が画面だけで分かる

**飽きない見た目について**：飽きの原因になりやすいのは、強い色や装飾よりも、「どの画面も同じに見えて、どこを見ればよいか分からない」ことと、「細かな線や揺れの騒がしさ」である。今のアプリは前者は小さく（画面ごとに見出しと形が違う）、後者に改善の余地がある（下線の多さ、見出しの枠）。そこで、Q1 の推奨どおり既存のトークンの中で、線と強弱を整える IMP-09〜IMP-12 を提案する。

### 5.2 IMP-10 フォーカスを移した見出しに枠を出さない（P2）

### 6.2 IMP-07 ブラウザに「保存の保護」を求め、その状態を表示する（P2）

- **課題**：このアプリのデータは localStorage にあり、ブラウザの区分では「消されうる保存」（best-effort）のままである。Chrome は、端末の空き容量が少なくなると、この区分のサイトのデータを丸ごと消すことがある。消えた場合に戻せるのは、最後に書き出したJSONまでになる。データを失う不具合ではないが、気づかないうちに起こりうる潜在的なリスクである
- **根拠**：`src/` に `navigator.storage.persist` の呼び出しが無い（検索で0件）
- **対策**：
  1. `src/domain/persistence.ts`（保存に触る唯一のファイル）に `requestPersistence(): Promise<"persisted" | "not-persisted" | "unsupported">` を足す。`navigator.storage?.persisted` が無ければ `"unsupported"`。すでに保護されていれば `"persisted"`。そうでなければ `navigator.storage.persist()` を1回呼び、結果を返す。例外は捕まえて `"unsupported"`
  2. `src/state/usePersistedState.ts` で、起動時に1回だけ呼び、結果を状態として持つ（PRプレビューでも呼んでよい。オリジン単位の設定のため）

  4. `eslint.config.js` は変えない（`navigator.storage` は今の禁止の対象外。触るのを `persistence.ts` に限ることは、コードのレビューで守る。気になるなら禁止の対象に `storage` を足し、`persistence.ts` だけ許す）
- **テスト**：`src/domain/persistence.test.ts` に、`navigator.storage` を差し替えて、①無いとき unsupported、②persisted が true のとき persist を呼ばない、③persist が true/false を返すとき、④例外のとき unsupported、の4件。外部と通信しないこと（`fetch` 等を呼ばない）は既存の禁止で守られる

- **文書**：`docs/design.md` 6.1 と 3.1 の ⋯ メニューの表に足す。`docs/weekly-review.md` 5章に「保存の保護が無効のとき」の行を足す（週次の書き出しを忘れない、の1行）

- **矛盾の確認**：外部と通信しない（端末の中の設定だけ）。警告ではなく状態の表示

### 6.3 IMP-08 読み込みの確認で、変更があるときは「書き出してから置き換える」を既定の操作にする（P2）

- **課題**：JSONの読み込みは置き換えで、取り消せない。今の確認画面は「最後に書き出した後に、このブラウザで変更があります」と［今のデータを書き出す］を出すが、押すかどうかは任意で、［置き換える］を押せばそのまま失う。PCとスマホで並行して変更した日（例：外出中にスマホで収集し、帰宅後にPCのファイルをスマホに読み込む）に、手順を1つ飛ばすと、スマホで入れた分が消える

- **対策**：

  3. 書き出せないとき（端末名が無い、読み取り専用）は今のまま理由を出し、［書き出してから置き換える］は出さない
- **テスト**：画面の部品なので単体テストは無し。書き出し → 置き換えの順と、書き出しに失敗したら置き換えないことは、判定を小さな純粋な関数（`importActions(changed, exportBlocked, exportedAt)` が出すボタンの種類を返す）に切り出してテストする

- **文書**：`docs/design.md` 6.2 の確認画面の図、`docs/weekly-review.md` 2.2 の手順3
- **効果**：並行して変更した日に、読み込みで失う前に必ず写しが残る（あとで読み込めば戻せる）。確認画面の数（7.1 の「確認は3つだけ」）は増やさない
- **矛盾の確認**：取り消せない操作であることは変えず、確認の画面の中の選択肢を増やすだけ。保存の仕組み・検証は変えない

### 7.1 IMP-14 Android のホーム画面にアイコンを置く（P1。運用だけ）

- **課題**：企画書3章の1は「思いついたものを即座に登録できる」ことを求める。Android で収集するまでに、ブラウザを開く → タブを探す（またはURLを入れる）の手数がかかる
- **対策**（**このPRで反映済み**）：`docs/weekly-review.md` 2.1 に、最初に1回だけ行う手順として「Android の Chrome で本番のURLを開き、⋮ →［ホーム画面に追加］でアイコンを置く」を足した。コードは変えない
- **完了の確認**：ホーム画面のアイコンから1回のタップで開き、入力欄に入れられる
- **効果**：収集までの手数が減る（G1）。Chrome は、ホーム画面に追加したサイトに保存の保護を許可しやすくなる（IMP-07 の効果も上がる）
- **矛盾の確認**：Chrome の機能を使うだけで、アプリをモバイルアプリにはしない（企画書5章）。全画面で開く設定（Manifest）は CR-006 として発注者の判断に回す

## 8. 実装するときの共通の約束

採否が決まった後に Claude Code が実装するときは、次を守る。

- 1つのPRは、関係する IMP を2〜4件にまとめた小さな単位にする（例：PR A＝IMP-03・04・05・10（CSS中心）、PR B＝IMP-01・02（ホームと一覧）、PR C＝IMP-07・08（保存と受け渡し）、PR D＝IMP-06・09・11・12（見た目））。PRの本文に「読みどころ」と、確認点ごとに関係する文書へのリンクを書く（CLAUDE.md 11.3・11.4）
- スキーマは v1 のまま変えず、`validateState` を厳しくしない（本番に実データがあるため）。IMP のどれも、保存するデータの形を変えない
- 依存パッケージ・外部との通信を足さない（CLAUDE.md 8.4）。IMP-07 の `navigator.storage` は端末の中の設定で、通信ではない
- 画面の文言は付録Bの用語集に揃える。ホームと一覧に、判定・警告・指示の文言を足さない（CLAUDE.md 4.3）
- 変えた画面は、PRプレビューで PC（1280px）と Android の幅（360px・412px）、ライト・ダークで確かめる。スクリーンショットは架空のデータだけで撮る（CLAUDE.md 8.3）
- `docs/design.md` の該当の章と変更履歴を直す。章を足したら目次も直す
- まとめて実装を終えたら `/security-review`（差分）を実行する（CLAUDE.md 13章）
