# 詳細ルール（v0.2 案）— docs/ai/詳細ルール.md に置く想定

AGENTS.md（核）から分けた詳細です。常時読み込みの対象ではないので、関係する作業の前に参照してください。
根拠：2026-11-15 の壁打ちで決めた複数 AI 開発の運用メモと、Gemini への確認回答（15問＋追加3問）。Gemini の回答は自己申告で、公式ドキュメントでの独立検証は未実施。

## 1. Gemini（Antigravity / VS Code）を使う前の準備

- PC 側で `git` と `gh auth login` を済ませておくこと。PR 作成はターミナルから git / gh CLI を呼ぶ方式
- **Settings の Account →「Enable telemetry」をオフにすること。** 個人プランのデフォルトのままだと、送ったコードがモデル改善に使われたり、人間のレビュアーに見られたりする可能性がある
- **仕事関連のコードや情報は個人の Gemini に渡さない。** 個人開発専用とする（消費者向け規約で、法人向けのデータ保護保証がないため）
- PR レビューの投稿は、最初はローカル Markdown に出力して洋平さん／ムーが確認してから投稿する

## 2. モデルの目安（固定しない）

- 設計など推論が要る役：Gemini Argon、Claude Opus
- 量のある実装：Gemini Hydrogen など高速なもの
- あくまで配分の目安。役割そのものはモデルに固定しない
- モデル事情の変化の例：Claude の Fable は期間限定で、2026-11-17 から Opus に変わる

## 3. 切り替えのきっかけと手順

| きっかけ | 切り替え方 |
|---|---|
| Claude のトークンが切れた | ムーが状態を引き継ぎ文書にまとめる → Gemini が同じブランチ／Issue の続きを担当する |
| 作業が並行して増えた | Issue 単位で担当を分ける。同じブランチは同時に触らない |
| 実装が終わった | レビューは実装者でない側の AI（またはムー）が担う |
| 判断の重い作業が来た | SE・レビューには Claude を温存し、量のある実装を Gemini に寄せるなど、ムーが配分を組み替える |

## 4. バトンタッチ時の指示文の型

- Claude Code → Antigravity（PC 側）：
  「git fetch して <ブランチ名> をチェックアウト（または Worktree で開いて）、docs/handovers/<ブランチ名>.md を読んで。残タスクを進めたあと、Built-in browser で画面表示とコンソールエラーがないか確認して PR を作成して。」
- Antigravity → Claude Code（クラウド側）：
  「docs/handovers/<ブランチ名>.md と直近のコミット差分を確認して。現在の実装に対するコードレビューとエッジケースのユニットテスト追加を行い、完了したら引き継ぎ文書を更新して push して。」

## 5. コーディング規約の置き場所

- 詳細なコーディング規約は、AGENTS.md ではなく `.agents/rules/` に条件付き読み込み（対象パスの glob 指定）で分ける
- v0.2 セットには例として2ファイルを用意した（.agents/rules/react-components.md、.agents/rules/testing.md）。Gemini のスリム版テンプレートの例をもとに、このリポジトリの実態（React 18、useReducer 中心、Tailwind なし、外部 API なし）に合わせて調整済み
- 中身はこのリポジトリの実態に合わせて書く（React 18、useReducer 中心、ドメインロジックは src/domain/ 等）。汎用テンプレートの具体値をそのまま持ち込まない
- コミットメッセージの形式は、このリポジトリの既存の運用（日本語の説明形式）を変えない
- 配置メモ：`docs/handovers/` には空ディレクトリ保持のため `.gitkeep` を置く

## 7. 旧 CLAUDE.md から引き継いだ詳細（2026-11-15）

旧 CLAUDE.md（記録 `docs/ai/開発指示書-フェーズ1.md`）のうち、今も有効なルールの細かいもの。核は AGENTS.md 9章にある。括弧の中は記録の章。

### 7.1 Git と PR

- 作業は Issue を立てて進める（AGENTS.md 3章）。作業のまとまりごとに計画を1回示して承認を得たら、その範囲の PR は、差分のレビューだけで進めてよい（10章・11.1）
- PR の本文に「読みどころ」（最初に読むとよいファイル・関数と、その理由）を書く（11.3）
- PR の「確認してほしいこと」には、確認点ごとに関係する文書へのリンクを付ける。リンクは完全な URL で、GitHub 上でクリックできる形にする（URL をコードブロックやバッククォートの中に置かない。リンクの文字にバッククォートを入れない）（11.4、2026-11-15 洋平さん）
- 1つの PR を小さく保つ。洋平さんが読むのは `src/domain/` と PR の「読みどころ」で、画面はプレビューで操作して確かめる（11.4）
- 文書に章・節を足したら、その文書の目次を直す（`docs/design.md` など）
- Claude Code の場合：コミットの Co-Authored-By の行にはモデル名を入れる（2026-11-03 洋平さん）

### 7.2 テストとセキュリティ

- セキュリティのテストは、名前に `@security` を含める（`npm run test:security` で選べるように。8.1）
- localStorage などの保存の API に触るのは `src/domain/persistence.ts` だけにする（ESLint で禁じている。8.2・12.6）
- 画面への表示はテキストとして行い、`dangerouslySetInnerHTML` を使わない。資料の本文などの URL を `href` に渡さない。本番ビルドの CSP（`connect-src 'none'` など）を保ち、外部のスクリプト・フォント・解析タグを使わない（8.3）
- ドラッグ＆ドロップで受け取るのは、このアプリのカードの id だけにする（7.2）
- 日付の判定は端末のタイムゾーンで行い、今の時刻は引数で受け取る。年度・四半期の境界のテストはタイムゾーンを `Asia/Tokyo` に固定する（5.2）
- まとまった実装を終えたら `/security-review` を実行する。`.claude/agents/` のレビュー用サブエージェントは、提出前の自己点検に使う（外のレビュアーの代わりではない）（9章・13章）
- 依存パッケージは react・react-dom と開発用のツールに留める。足すときは理由を示して洋平さんの承認を得る（8.1。AGENTS.md 7章）

### 7.3 画面と UX

- ホームは状態の表示に徹する。「〜しましょう」「滞留しています」などの結論・指示・警告は出さない（判定して知らせるのはフェーズ2。4.3・7.2）
- 確認ダイアログを出すのは、JSON の読み込み・保存データの消去・プロジェクトの削除だけ。日常の操作は確認を出さず、直後の「元に戻す」で救う（7.1）
- 色だけで情報を伝えない。キーボードだけでも操作できる。内部の値（`active`・`todo` など）を画面に出さない（7.1）
- PC と Android の両方のブラウザで使う。幅 375px 程度で、収集・明確化・次のアクション・置き場・プロジェクトを横スクロールなしに使える。文書には機種名を書かず「Android」と書く（7.1）
- 見た目は `src/index.css` のデザイントークンとライト・ダークの切替を使い、新しいデザインはしない（7.1）

### 7.4 進め方

- 設計の理由（なぜこの形にしたか）を `docs/design.md` に残す（1.3・11.3）
