- **成果物**：`docs/retrospective.md`（節目4の提出物はこの1つ。計画 3章、CLAUDE.md 12.5）

## 4. チェックリスト

### 4.1 開始前に1回だけ（10分。計画 2.2）

- [ ] PCとスマホ（Android）の両方で本番のURLを開き直し、最新の版が出ることを確かめた
- [ ] 両方の端末に端末名（「PC」「スマホ」など）が付いている（手順書 2.1 の3）
- [ ] 受け渡し用のフォルダの共有の設定が、自分だけになっている（手順書 2.1 の2）
- [ ] 今のデータを1回書き出し、バックアップの保存先（リポジトリのフォルダの外）に置いた（手順書 3章）
- [ ] 記録用のメモを手元（スマホのメモのアプリなど。リポジトリの外）に用意し、5章の書式を貼った

### 4.2 毎日（計画 2.3）

- [ ] 思いついたときに、上の入力欄に入れて Enter（収集。どの画面からでも）
- [ ] 収集箱の［明確化を始める］で振り分けた（1日1回以上が目安）。空にできたら「収集箱を空にした回数」に1つ数える（空にできない日があってもよい）
- [ ] 次のアクションを見て、終わったものを完了にした
- [ ] 1日の終わりに、記録のメモに1行書いた（5章）

### 4.3 使う端末を替えるとき（手順書 2.2）

- [ ] 使い終わった端末で［書き出す］→ ファイルを受け渡し用のフォルダへ
- [ ] 次に使う端末で ⋯ →［JSONを読み込む］→ 確認画面で端末名と日時を見てから［置き換える］
- [ ] 受け渡し用のフォルダから、読み込んだファイルと、それより古いファイルを消した
- [ ] 記録の「受け渡しの回数」に1つ数えた

両方の端末で並行して変更しない（読み込んだ側の変更は消える。手順書 2章）。

### 4.4 週次レビュー（7日目の土曜、30〜60分。手順書 1章）

- [ ] ① 収集箱：［明確化を始める］で空にした（決められないものは「いつか・多分」へ）
- [ ] ② 次のアクション：終わったものを完了に、要らないものは削除、合わないものは［移す…］
- [ ] ③ 連絡待ち：返事が来たものを完了に、催促が要るものは次のアクションを足した
- [ ] ④ プロジェクト：「次のアクション N件・連絡待ち M件」を目で見て、要るものに次の一手を足した。終わったものは［完了にする］
- [ ] ⑤ いつか・多分：始めたいものを［移す…］、要らないものは削除した
- [ ] ⑥ 年次目標・四半期シート、ロードマップ：今の四半期の重点テーマと主要プロジェクトを見直した。あわせて、ロードマップのテーマの行ごとの並びを1回眺めた（7章の観点2）
- [ ] ⑦ ［書き出す］で JSON を書き出し、バックアップとして保存した（手順書 3章）
- [ ] 記録のメモに、週次レビューにかかった時間、迷った順番、直した件数を書いた（計画 2.4）

### 4.5 週の終わりに（運用の翌日）

- [ ] 記録のメモを見直し、タスク・プロジェクトの内容が入っていないことを確かめてから、スレッドに貼った（6章）
- [ ] 7章の観点1・3を振り返り、気づきをメモに足した
- [ ] （実装担当）SEC-002 を再確認する（計画 4章。発注者は、直した版を取り込む Dependabot のPRが出ていれば、CI が通っていることを見てマージする）
- [ ] 1章の完了条件の3つに、チェックが付くかを見た

## 5. 記録の書式

計画 2.5 の列です。メモに1日1行で書きます。

```
日付｜使った端末（PC／スマホ／両方）｜収集箱を空にした回数｜受け渡しの回数｜週次レビュー（した／しない）｜JSONを書き出した（した／しない）｜作業時間（分）｜気づき（画面と操作の名前で1行）
```

- 作業時間は、収集・明確化・整理・週次レビューのおおよその合計
- 気づきは、迷った・困った・よかった場面を、画面と操作の名前で書く（架空の例：「明確化の2つ目の質問で、プロジェクトか迷った」）
- 書くのは件数と気づきだけ。タスクやプロジェクトの内容は書かない

## 6. 実装担当へのフィードバックの書式

### 6.1 記録の提出

- 運用の翌日に、5章のメモを（内容が入っていないことを見直してから）スレッドに貼る。実装担当は書き写さずに工程ごとに要約して、振り返りの下書きを作る（計画 2.5）

### 6.2 不具合の報告

次の項目で書きます。実データの JSON・スクリーンショットは添付しません（計画 2.6）。

```
画面の名前｜した操作｜起きたこと｜使った端末（PC・スマホ）｜毎回起きるか
```

| 起きたこと | いつ知らせるか（計画 2.6） |
| --- | --- |
| データを失う・保存できない・起動時に読めない | **週の途中でも、すぐスレッドで知らせる**。先に JSON を書き出しておく。運用は止めずに続け、その日のメモにも書く |
| それ以外の不具合 | 記録のメモに書いて運用を続ける。週の後にまとめて扱う |
| 改善の案・欲しい機能 | 記録のメモに書く。週の後に、実装担当が変更要求（`docs/change-requests.md`）に記録する。実装はせず、採否は発注者が決める |

困ったときの手当て（保存できない帯が出た、読み取り専用になった、など）は手順書 5章にあります。

## 7. 気づきを書くときの観点

このツールは、タスク管理の仕組み化（年・四半期の層と、日々の層を1つの仕組みで見る）の道具として作りました。1章の回数の基準とは別に、気づきを書くときに次の3点を思い出してください。新しい記録の欄や手順ではなく、5章の「気づき」の列を書くときの見方です。

1. **信頼できる置き場になったか**：この1週間、頭の中や別のメモに、タスクを二重に覚え続けていなかったか。並行した覚え書きが残っていたら、その場面を書く
2. **テーマの偏り**：仕事と私生活を分けずに7つのテーマで見る作りなので、週次レビューの⑥で、テーマの行ごとの偏りを1回眺めて、気づいたことを書く。ツールはテーマごとの件数を数えないので（CLAUDE.md 4.3）、数えるなら目で数える。書くのは件数だけで、内容は書かない
3. **既存の運用との接点**：土曜は、ツールの週次レビューと、既存の週次レポートの相談が重なる。つながって楽だったか、二度手間に感じたかを書く。あわせて、朝にツールを開いて今日のアクションを選ぶ動きが起きたかどうかも書く（フェーズ2で日次の機能が要るかの判断材料になる）
