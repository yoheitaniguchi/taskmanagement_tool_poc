## 2. 運用の1週間

### 2.1 期間

推奨は前倒しで、**2026-11-08（日）〜11-14（土）の7日間**（7日目の土曜に週次レビュー）。振り返りは 11/15（日）〜11/17（火）（7.1 の1）。
11/8 中にこの計画を承認できなければ、11/9（月）〜11/15（日）にずらす。その場合も週次レビューは 11/14 の土曜（6日目）に行い（G7 の基準は「7日間のうちに1回」なので満たせる）、振り返りは1日ずつ後ろにずらす（11/16〜11/18）。

### 2.2 始める前に1回だけ（運用の前日か初日の朝、10分）

1. PCとスマホ（Android）の両方で、本番のURLを開き直し、最新の版が出ることを確かめる
2. 端末名（「PC」「スマホ」など）が付いていること、受け渡し用のフォルダが自分だけのものであることを確かめる（`docs/weekly-review.md` 2.1）
3. 今のデータを1回書き出して、バックアップの保存先（リポジトリのフォルダの外）に置く
4. 記録用のメモ（2.5）を、手元（スマホのメモのアプリなど。リポジトリの外）に用意する

### 2.3 毎日すること

ふだんのタスク管理として使うだけで、運用のための特別な作業は記録（1日1〜2分）だけ。

| いつ | すること |
| --- | --- |
| 思いついたとき | 上の入力欄に入れて Enter（収集。どの画面からでも） |
| 1日1回以上が目安 | 収集箱の［明確化を始める］で、1件ずつ振り分ける。空にできたら、記録の「空にした」に1つ数える。空にできない日があってもよい（7日間で2回以上が基準） |
| 作業の合間 | 次のアクションを見て、終わったものを完了にする |
| 使う端末を替えるとき | 使い終わった端末で書き出し、次の端末で読み込む（`docs/weekly-review.md` 2.2）。記録の「受け渡し」に1つ数える |
| 1日の終わり | 記録のメモに、その日の1行を書く（2.5） |

### 2.4 週次にすること（7日目の土曜、30〜60分）

`docs/weekly-review.md` 1章の ①〜⑦ の順に見て回る（①収集箱を空にする → ②次のアクション → ③連絡待ち → ④プロジェクト → ⑤いつか・多分 → ⑥年次目標・四半期シート、ロードマップ → ⑦JSONを書き出す）。
かかった時間と、どの順番で迷ったか・何を直したかの件数を、記録のメモに書く。

### 2.5 記録の付け方

ツールには記録の機能が無いので（CLAUDE.md 3章 G7）、発注者が手元のメモに、1日1行で書く。**件数と短い気づきだけ**を書き、タスクやプロジェクトの内容は書かない。

```
日付｜使った端末（PC／スマホ／両方）｜収集箱を空にした回数｜受け渡しの回数｜週次レビュー（した／しない）｜JSONを書き出した（した／しない）｜作業時間（分。収集・明確化・整理・週次レビューのおおよその合計）｜気づき（迷った・困った・よかった場面を、画面の名前で1行）
```

- 「気づき」は、たとえば「明確化の2つ目の質問で、プロジェクトか迷った」「スマホでロードマップのカードを移すのが分かりにくかった」のように、画面と操作の名前で書く
- 週の終わりに、このメモを（実データが入っていないことを見直してから）このスレッドに貼ってもらう。実装担当がそれを元に振り返りの下書きを作る（3章）
- 実装担当は、気づきの1行をそのまま書き写さず、工程ごとに要約して振り返りに書く。タスクやプロジェクトの内容らしき言葉があれば、振り返りにもPRの本文にも書かず、先にこのスレッドで発注者に確かめる
- 振り返りのテンプレートの日別の表（`docs/templates/retrospective.md`）は、このメモの列に合わせて直す（3章）

### 2.6 運用中に見つかったことの扱い

週の途中でツールを変えると、1週間の運用の結果が読みにくくなる。そのため、直すのは原則として週の後にする。

| 見つかったこと | 扱い |
| --- | --- |
| データを失う・保存できない・起動時に読めない不具合 | すぐこのスレッドで知らせてもらう（先にJSONを書き出してもらう）。実装担当が直してPRを出し、発注者が差分を見てマージする。運用は止めずに続け、その日のメモに書く |
| それ以外の不具合（設計案どおりに動かない） | メモに書いて運用を続ける。週の後にまとめて直す（7.1 の3） |
| 改善の案・欲しい機能 | 実装せず、`change-request-reviewer` で確かめてから `docs/change-requests.md` に記録する（CLAUDE.md 11.2）。フェーズ2の③④に当たるものは「フェーズ2候補」と書く。採否は発注者が決める |

- 不具合を直すときも、スキーマは v1 のまま変えず、`validateState` は厳しくしない（本番に実データがあるため。節目3の計画 2.1）
- 不具合の報告にも実データを書かない（どの画面で、何をしたら、何が起きたか）。実データのJSON・スクリーンショットは添付しない。実装担当は、架空のデータで再現して確かめる。PRプレビューで確かめるときも、実データを読み込まない（`docs/weekly-review.md` 4章）
